# 配图链路修复：粘贴暂存图失效可见化 + 封面误入正文 + 配图计数口径

## Goal

修复预览页配图链路的三个关联缺陷，使用户对「配了哪些图、哪些已就绪、哪些失效」始终有准确认知，且任何失效都**可见、可处置、可阻止误发布**：

1. 剪贴板粘贴的暂存图在「非用户主动」的页面重载后**静默消失**（图没了、也没任何提示）；
2. 在 AI 生图里点「设为封面」的图，同时被自动插进了正文；
3. 预览工具栏「配图 X/Y」与发布页「插图 N 张」计数口径不一致、且都不准确。

## Background（现状与根因，均为代码级已确认）

- **粘贴图机制**：粘贴图片时不即时上传，正文写入占位 token `![](sparkora-img:<id>)`，图片本体只存在前端**内存单例** `frontend/src/utils/pendingImageStore.js`（不持久化）；预览时 `usePreviewRender` 把 token 的 `src` 投影为内存 `blob:` URL。点预览页「去发布」时 `usePendingImageFlush.flushPendingImages` 逐张上传图床并把 token 替换为公网 URL，随后保存正文、跳发布页。
- **Bug1 根因**：会落库的正文可能长期含 token，而 token 的实体只活在内存。任何重载（手动刷新 / 浏览器标签长时间后台被丢弃后重载 / Vite HMR 整页 reload / 崩溃恢复）都会清空内存，token 无法解析。当前**无任何用户可见提示**：预览 `mapTokenSrc` 查不到条目时原样保留 `src="sparkora-img:<id>"`，渲染成破图/空白，视觉上等同「图消失」。
  - 诊断发现（待实测确认）：`flushPendingImages` 先上传（图床可见）→ 再 `saveContent` 持久化 URL 版正文。若「上传成功」与「URL 版正文保存成功」之间发生重载，则图床有对象、正文仍是 token → 重载后图消失。这正是用户描述的「肉眼可见上传到图床，但过一会图没了」。
- **Bug2 根因**：`StepPreview.vue` 的 `onGenerated` 在「首次生成且 n=1」时**无条件**调用 `insertBodyImage` 自动插入正文；用户随后在候选卡片点「设为封面」，同一张图就同时是封面 + 正文插图。
- **Bug3 根因**：
  - 预览工具栏 `配图 {insertedCount}/{snapshotCount}`：分母 `snapshotCount = imgSnapshot.images.length`，而 `ImageService.projectImages` 的 `images` = **封面 + 正文引用图**（封面被算进分母）；分子 `insertedCount` = 快照图里 URL 出现在正文中的数量，只能覆盖「已在快照里的图」。
  - 手动插图（`insertBodyImage`：图库插入 / AI 插入）**只写 markdown、不登记** `sparkora_article_version_image`（`docs/spec/image.md` §7.7 已知债务），导致发布页 `插图 {bodyImageIds.length}` 少算；粘贴图上传后也未登记。
  - 结论：分子/分母/登记表三者口径各不相同，且都没以「正文实际引用」为准。

## Requirements

### R1 — 失效/未上传的粘贴图必须可见、可处置、可阻止误发布（Bug1）

- **R1.1 失效可见化**：预览渲染时，正文中任何**无法解析**（内存无对应条目）的 `sparkora-img:<id>`，必须渲染为明确的失效占位块（虚线框 + 中文文案，如「粘贴图片已失效，请重新粘贴」），**不得**静默留空/破图。
- **R1.2 全局警示**：只要当前正文含失效 token，预览页顶部展示可见警示条，说明原因与处置（重新粘贴，或若仍可上传请点「去发布」）。
- **R1.3 阻断误发布/误复制**：正文含失效 token 时，「去发布」「复制排版」「发布页确认发布」均须明确阻止并给出可执行提示（保留既有后端 token 防呆作为兜底）。
- **R1.4 已上传即不丢**：`flushPendingImages` 必须保证「token→URL 的正文替换已**持久化成功**」才算完成；保存失败时**中止跳转**、保留 token、明确报错，供重试。即：图床已收到对象的图，正文不得停留在 token 版本。
- **R1.5 非主动刷新诊断与兜底**：定位「长时间未动页面自动刷新」的真实触发源（浏览器标签丢弃 / Vite HMR 整页 reload / 应用逻辑）并记录结论；应用侧若能规避则规避，不能规避时至少做到「存在未上传暂存图时，离开/卸载前给出离开确认提示」。

### R2 — 封面不再误入正文（Bug2）

- **R2.1** 移除 AI 生图「首次生成 n=1 自动插入正文」的行为；生成完成后一律由用户显式点「插入正文」。
- **R2.2** 「设为封面」只改变封面，不插入也不删除正文内容。

### R3 — 配图计数统一口径（Bug3）

- **R3.1 唯一口径 = 正文实际引用**：以解析当前正文 markdown 的图片引用（`![](...)`，按目标字符串去重）作为「正文插图数」的唯一计算依据。
- **R3.2 两处一致**：预览工具栏「配图」角标与发布页「插图 N 张」使用**同一计算口径**，且**封面不计入**正文插图数。
- **R3.3 补登记**：手动插图与粘贴图上传成功后，在能拿到图库 id 时登记 `sparkora_article_version_image`（修 §7.7 部分债务），使关联表与正文引用一致（引用保护/删图校验不误判）。
- **R3.4 待上传与失效区分**：正文中的未上传 token 不计入「已就绪插图数」，由 R1 的警示单独呈现（避免用户以为发布时会带上）。

## Acceptance Criteria

- [ ] **AC1**（R1.1/R1.2）粘贴 3 张图 → 手动刷新页面：正文对应 3 处显示失效占位块、顶部有警示条，均非空白。
- [ ] **AC2**（R1.3）含失效 token 时：点「去发布」、点「复制排版」、在发布页点「确认发布」均被阻止且有可执行的中文提示。
- [ ] **AC3**（R1.4）粘贴图 → 点「去发布」全部上传成功 → 刷新页面：图片仍正常显示（正文已是图床 URL 版）。
- [ ] **AC4**（R1.4）模拟 URL 版正文保存失败：不跳转发布页、正文保留 token、给出错误提示，可再次点「去发布」重试成功。
- [ ] **AC5**（R2.1/R2.2）AI 文生图 n=1 生成 → 点「设为封面」：正文**不出现**该图，封面设置成功；需插图时点「插入正文」才入正文。
- [ ] **AC6**（R3.1/R3.2）正文插入 3 张图库图 + 1 张已上传粘贴图、并设 1 张封面：预览角标与发布页均显示「插图 4 张」，封面不计入；口径一致。
- [ ] **AC7**（R3.3）任一来源插入正文后，`GET /api/projects/{id}/images` 的 `bodyImageIds` 与实际正文引用一致。
- [ ] **AC8**（R1.5）记录「自动刷新」触发源的诊断结论；若为应用可规避项则已规避；否则存在未上传暂存图时离开有提示。
- [ ] 回归：不含 token、未设封面等历史路径行为不变；`npm run build` 与 `mvn -q -DskipTests compile` 通过。

## Constraints

- 遵循既有决策：暂存图**不持久化**（不引入 IndexedDB 存 Blob）；上传唯一触发点仍是预览页「去发布」。本任务**保持该策略**，只解决「丢失静默」与「已上传却丢」。
- 不新增第三方依赖；前端走后端调用统一走 `frontend/src/api/index.js` 具名导出。
- 后端代码/注释/文档用中文；前端页面用 Element Plus；移动端触控目标 ≥44px。
- 表结构如需变更走 Flyway 新迁移（本任务预期**零 DB 迁移**：登记复用既有接口）。
- 规格同步：`docs/spec/image.md`（§7.7 债务、§8 页面职责）、`docs/spec/preview.md`、`docs/spec/publish.md`；如产生可复用约定，补 `.trellis/spec/frontend/index.md`。

## Out of Scope

- 暂存图跨刷新/跨设备的持久化（用户明确保持「刷新丢临时图」策略）。
- 粘贴以外的拖拽入库；
- 关联表彻底改为「以正文解析为准」的大规模重构（仅做必要的登记补充）。

## Open Questions（实现阶段实测收敛）

- R1.5 的「自动刷新」触发源（标签丢弃 vs HMR vs 应用逻辑）——决定兜底手段是 `beforeunload` 提示还是应用侧修复。
- 工具栏角标最终展示形态（如 `配图 4` 或 `配图 4 · 2 待上传`）——以「不误导」为准，实现时按 AC6 定稿。
