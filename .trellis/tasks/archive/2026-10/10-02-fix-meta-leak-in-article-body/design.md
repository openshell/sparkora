# 设计：正文元话语泄漏（suggestion 泄漏 + 读者视角契约 + 确定性清洗）

## 1. 问题本质

内部工件 `brief.fact_risks[].suggestion` 是**写给作者的第二人称祈使指令**（「此表述必须删除或改为 X」「建议正文以 Y 为主」）。写作链路把它当素材注入后，模型把它**改写成第三人称陈述**放进正文——祈使句变「已核实的客观事实陈述」，于是「手册未披露…完成率无法计算」被当成对读者的结论说出来。

关键点：`claim` 是**陈述性断言**（可安全用作「禁止断言」清单），`suggestion` 是**祈使指令**（必然被复述）。二者不可混用。

## 2. 边界与职责

| 层 | 职责 | 落点 |
|---|---|---|
| R1 停止泄漏源 | 只投 `claim`，且以「禁写断言」框架投 | `DeepWriterService.write`、`VersionService.buildUserPrompt` |
| R2 读者视角契约 | system prompt 层面禁止元话语、禁止解释缺失 | 同上两处 system |
| R3 确定性清洗 | prompt 治不了 100%，落库前兜底 | 新增 `MetaLeakCleaner`（`com.sparkora.service`，纯静态） |

**不动的层**：`BriefService`（简报面向作者，说「手册未提供」是正确的）、`fact_sheet.entries` 注入（数值唯一来源，必须保留）、user prompt 块头文案（R4，测试锁定）。

## 3. R1：factRisks 注入改造

### 3.1 数据流

```
brief.fact_risks = [{"claim":"…","riskLevel":"high","suggestion":"…祈使句…"}]
      │
      ├─ 旧：整块 JSON → user prompt「事实风险:」  ← 泄漏源
      └─ 新：只抽 claim → 「【禁止写入正文的断言】(以下断言无数据支撑，正文禁止出现或作为结论陈述)：\n- …」
```

### 3.2 契约

- 新增静态方法 `factRiskClaims(String factRisksJson)`：
  - null/空白/`[]`/`{}` → 返回 null（**不注入**，与 `appendBriefSection` 现有跳过语义一致）
  - JSON 数组 → 逐项取 `claim`（textual 直取；非 textual 或缺失 → 跳过该条），`claim` 空白跳过
  - 解析失败/非数组 → **返回 null 并 log.warn**（不按原文追加，避免畸形数据把祈使句带回来）
  - 全部 claim 为空 → null
- 深度链路：`DeepWriterService.java:266` 的 `appendBriefSection(user, "事实风险", ...)` 替换为 `appendForbiddenClaims(user, b.getFactRisks())`。
- 多版本链路：`VersionService.java:296` 的 `- 事实风险点（写作时注意表述，按建议弱化或标注）：%s` 与 `:303` 的 `nv(b.getFactRisks())` 移除，改为同格式禁写清单块（同一段 helper 文本，两链路共用）。

### 3.3 为什么不用「让 suggestion 换个写法」

suggestion 的语义就是祈使指令；只要祈使句进入正文素材区，模型就有动机复述/改写它。唯一安全做法是**不投 suggestion**。简报侧因此不改（作者看简报时需要祈使句）。

## 4. R2：读者视角铁律（新增常量，两链路共用文本）

在两条链路的 system prompt 追加（`DeepWriterService` 在排版铁律后、`VersionService` 在 layoutRules 后）：

```
读者视角铁律(必须遵守):你只写给读者看,不存在"资料/手册/简报"这些概念。
- 正文禁止出现下列内部话术:手册、事实手册、简报、大纲、事实风险、断言清单、未收录、未提供、无法计算、待核实、不应作为结论、据手册、知识库未覆盖。
- 资料未覆盖的论点直接不写;确需提及就用不带数据来源说明的定性表述一句带过。
- 禁止在正文中解释"为什么没有这个数据"或"哪些结论不能下"——这类内容属于创作过程,不面向读者。
```

设计要点：
- 用**黑名单 + 行为指令**双写，而非仅黑名单——只禁词不禁行为，模型会换词绕开。
- 「不存在『资料/手册/简报』这些概念」先行切断模型把内部工件当叙述对象的动机。
- 放在 system（约束力强于 user 素材区），且紧邻 layoutRules 收尾，避免被长 user prompt 稀释。

**取舍**：不改铁律 2「手册未覆盖的参数，用定性表述」与块头「事实手册(数值唯一来源):」。理由：(a) `DeepWriterServicePromptTest` 多处逐字锁定；(b) 该措辞是**给模型的约束语**而非素材，泄漏主因是 suggestion 而非块头；(c) R3 兜底足以覆盖残余。若实测仍漏，再迭代（见 §7 演进）。

## 5. R3：`MetaLeakCleaner` 设计

### 5.1 位置与形态

`com.sparkora.service.MetaLeakCleaner`，与 `LayoutRules` 同范式：**纯静态、无状态、无 Spring 依赖、可单测**。

```java
public final class MetaLeakCleaner {
    public record CleanResult(String content, List<String> removed) {}
    public static CleanResult clean(String markdown);
}
```

`removed` 返回被删原文，供调用方 `log.warn` 落审计（不落库、不给前端，避免新增契约）。

### 5.2 匹配策略

**句级删除**，不是行级、不是整篇丢弃：
1. 按 Markdown 段落切分（空行分隔），保留段落内的换行结构（软换行不切）。
2. 每段内按中文句读切分：`。！？!?` + 后续闭合引号/括号 + 换行保留符。
3. 逐句过 `META_PATTERNS`；命中 → 丢弃该句，记入 `removed`。
4. 段内全部句子被删 → **整段丢弃**（避免留下空标题下的空段）。
5. 重组：连续空行压成 1 个；行首行尾空白裁剪；**不改动未命中的句子内容**（零改写，保守）。

### 5.3 元话语模式（保守，宁漏不误伤）

```java
手册未提供|手册未披露|手册未收录|手册未覆盖|事实手册未…   ← 主泄漏
(本文|正文|文中)?(无|没有|未)(数据|依据|出处)(支撑|来源)
无法计算|不可计算(完成率|占比)
不应作为(结论|输出)|不得作为结论
缺乏[^。]{0,8}可比数据|未提供[^。]{0,8}数据|未收录于?
待核实(?!.*(?:官网|官方))
知识库未覆盖|知识库(检索)?失败
(本文|本报告|下文)(不|无法)(作|提供|给出)结论
置信\s*0\.\d+|仅单一\s*WEB\s*源
证据:.*仅单一
```

**误伤控制**：
- 每条模式都以**内部词 + 缺失/否定**的组合为特征，不匹配「详细参数以官方发布为准」「据媒体报道」这类正常归因句。
- `待核实` 加了否定前瞻（`官网/官方`）——「以官方发布为准，参数待核实」这类正常句保留。
- 单测必须包含一组「必须原样保留」的反例清单（AC4）。
- 风险自认：`未提供[^。]{0,8}数据` 可能误伤「该配置未提供数据接口」——汽车垂类正文极罕见，命中也只是删一句，代价可接受。

### 5.4 接入点

| 链路 | 接入 | 位置 |
|---|---|---|
| 深度 | **必须** | `DeepWriterService.write`：`content = cr.content()` 之后、⑥ `verifyNumbers` **之前**（清洗后再回查，避免对已删句做数值误报） |
| 多版本·主题分支 | 接入 | `VersionService.generateOne`：`contentMd` 取出后、`contentMd.isBlank()` 校验后（**先校验后清洗**，清洗致空不回写空正文） |
| 多版本·仿写分支 | **不接入** | 仿写正文源自用户原文，`stripImages` 之外的二次改写有误删作者原意风险 |

## 6. 兼容与回滚

- **接口契约零变更**：无 REST/DTO/DB 变更，`/deep/generate`、`/generate/versions` 响应不变。
- **prompt 逐字兼容性**：R4 保证了铁律 1~3、排版铁律、块头文案不变；变化仅限「事实风险块 → 禁写断言块」与 system 追加段。
- **回滚形状**：三处改动相互独立——回滚 R1（恢复 `appendBriefSection`）、R2（删常量）、R3（不调 `clean`）可单独 revert，均不影响其他。清洗器为纯函数，误伤时可快速调整 `META_PATTERNS` 而无需回滚 prompt。
- **不做存量改写**（Out of Scope）：生产数据不可逆副作用，且编辑页支持人工改正文。

## 7. 已知局限与演进

1. **prompt 非确定性**：R2 是约束而非硬保证，同一模型仍可能偶发漏词 → R3 是最终保证线。若清洗命中率长期 > 0（正常正文不该命中），说明 R2 文案需要加强措辞（迭代点）。
2. **清洗的语义损失**：删句而非改写，可能在极少数情况下删掉半句有用信息。汽车垂类元话语句通常自成句（「需要说明的是，…无法计算」），删除损失可控。
3. **仿写分支未覆盖**：仿写 prompt 不注入 factRisks（`buildImitationPrompt`），无泄漏源，故不接清洗器——避免误删作者原文。
4. **历史正文**：version 44/19/15 保持原样，由编辑页人工处理；如用户要求，另开一次性脚本（需人工确认清单）。
