# BYD 小程序圈子可选携带

## Goal

修正 BYD 王朝小程序发布页的产品模型与术语：系统中只配置一个固定圈子，每次推送可以明确选择“携带圈子”或“不携带圈子”，并完成开发服务器部署与验收。

## Background / Confirmed Facts

- 用户只在一个比亚迪王朝车友会圈子发帖，但部分内容需要不带圈子。
- 比亚迪王朝小程序中的官方业务名称是“圈子”，不应继续在用户界面使用“车友会标签”。
- 项目创建时已通过 `channel=byd_miniapp` 与公众号项目区分，本任务不改变渠道判定。
- 当前页面把 `clubTagOptions` 渲染为下拉框；服务器默认圈子配置为空时页面无可选项并且下拉框禁用。
- 比亚迪草稿协议实际仍使用 `clubId` / `clubTitle` 字段，本任务保留协议字段名，只调整产品语义和用户可见术语。

## Requirements

### R1 页面交互

- BYD 发布页不再展示多选项下拉框。
- 页面展示单个“圈子”配置：一个“携带圈子”开关，以及服务端配置的圈子名称。
- 服务端圈子配置完整时，开关默认开启；用户可以关闭后推送不带圈子的文章。
- 服务端圈子配置不完整时，开关禁用并明确提示配置缺失；用户仍可推送不带圈子的文章。
- 用户手动切换后在轮询刷新期间保留当前选择；配置失效时自动关闭开关，不能提交无效圈子。

### R2 状态接口

- `GET state` 返回圈子是否配置、固定圈子 ID、固定圈子名称及不可用原因。
- 不再要求前端根据多个 `clubTagOptions` 做选择。
- 保持必要的旧字段兼容，避免已打开旧页面立即失效。

### R3 创建任务接口

- 新前端显式提交 `useCircle`：
  - `true`：携带服务端固定圈子。
  - `false`：不携带圈子。
- 携带圈子时由服务端读取固定配置，前端不再提交可被篡改或过期的 ID/名称。
- 不携带圈子时 payload 仍显式写入 `clubId=null`、`clubTitle=null`，与旧任务缺少字段区分。
- 旧版请求字段可兼容，但只能使用服务端当前固定的完整圈子对。

### R4 服务端与 Agent

- 服务端只允许一个固定圈子；不再把项目历史圈子作为第二个可选圈子。
- 服务端配置不完整时，只有“携带圈子”的请求失败；“不携带圈子”仍可创建任务。
- 成功 v2 推送后将本次实际使用的圈子对回写项目，用于审计和后续展示；失败任务不修改。
- Agent 继续消费 payload 中的 `clubId` / `clubTitle`，不得改变 MMKV 草稿协议。
- 用户可见错误和说明统一使用“圈子”，内部变量及比亚迪协议字段可保留 `club`。

### R5 配置与部署

- 开发服务器使用固定圈子：`220 / 四川迪友会`。
- 更新 `.env.example` 与部署文档，说明这两个变量配置的是固定圈子。
- 完成本地测试、提交、推送、镜像构建和开发服务器部署。

## Acceptance Criteria

- [ ] BYD 发布页不存在“车友会标签”下拉框或“车友会标签”用户可见文案。
- [ ] 配置完整时页面显示“圈子：四川迪友会”和“携带圈子”开关，初始为开启。
- [ ] 关闭开关后创建的任务 payload 同时包含空 `clubId` 与空 `clubTitle`。
- [ ] 开启开关后创建的任务 payload 使用服务端固定圈子 `220 / 四川迪友会`。
- [ ] 无完整圈子配置时页面显示明确提示，开关不可开启，但仍可创建不带圈子的任务。
- [ ] 服务端与 Agent 对半套圈子字段继续拒绝，且错误文案使用“圈子”。
- [ ] Java、Agent pytest、前端构建和 `git diff --check` 全部通过。
- [ ] 开发服务器 backend 为 healthy、frontend HTTP 为 200、backend 鉴权探活为 401。
- [ ] 部署后的容器内两个圈子变量均非空，且部署提交与远端功能分支一致。

## Out of Scope

- 多圈子目录、圈子搜索或按项目切换不同圈子。
- 重命名比亚迪协议字段 `clubId` / `clubTitle` 或数据库历史列。
- 修改 BYD 图片/视频上传链路。
- 修改微信公众号发布逻辑。
- 改动项目渠道创建与判定规则。

## Notes

- 固定圈子以服务端环境变量为唯一来源；Windows Agent 本地圈子配置只承担旧 payload 兼容，不作为发布页选项来源。
