# 发布超时阈值不足导致「假失败」+ 真实草稿已写入（09-27-wenyan-stale-conn）

> 任务名沿用创建时的初版判断；实际根因与初版假设**不同**，以本文为准。

## 背景（现象）

项目 54（比亚迪闪充桩）发布到公众号草稿箱失败，前端报「发布失败」，项目
`last_publish_error` = `发布请求失败: Error while extracting response for type
[java.lang.String] and content type [application/octet-stream]`。用户先后尝试两次，
均失败。

## 根因（已实测确认）

`/publish` 实测需要 **43.4 秒**，而后端读超时是 **30 秒**（`WENYAN_MCP_PUBLISH_TIMEOUT_MS`
未配置于 `.env`，跑的是 `application.yml` 默认 `30000`）。

直接绕过本项目客户端、以 180s 超时打 wenyan-server 实测：

```
POST /upload   → 200，fileId=3e5c2ccf-….json
POST /publish  → HTTP 200  TOTAL=43.41s
                 {"media_id":"7lVDB5t872UUwRzsEuriFuDE-…"}
```

项目侧两次失败的日志，两次都精确在 **30.016 秒**断掉：

```
21:12:34.392  publish 开始      →  21:12:44.154  /publish 请求失败   (9.76s)
21:41:09.645  publish 开始      →  21:41:39.661  /publish 请求失败  (30.016s)
```

**关键后果**：客户端 30 秒放弃，**服务端仍继续执行并在 ~43 秒成功写入草稿**。
即「前端报失败，但公众号草稿箱里已经有这篇文章」。用户据此重试 → **每次重试都多一篇重复草稿**。
这使「重试」这一自然排障动作本身成为制造脏数据的动作。

## 已排除的假设（记录以免重复排查）

| 假设 | 排除依据 |
|---|---|
| 客户端复用失效 keep-alive 连接导致 EOF | 用真实 `java.net.http.HttpClient` 复现：请求→`sleep(6000)`（> 服务端 `Keep-Alive: timeout=5`）→请求 = `200`，**未复现**；JDK 会自行丢弃失效连接 |
| `Connection: close` 是可行修法 | JDK 直接抛 `IllegalArgumentException: restricted header name: "Connection"`，需全局 JVM 参数 |
| 社区主题 CSS 外链图片拖慢发布（09-11 先例） | `grep -nE "url\(https?://" src/main/resources/wenyan-themes/*.css` → **零命中** |
| 7 张正文图下载慢 | 逐张实测全部 200，合计 ~2.5s / 17MB（0.13~0.80s 每张） |

**环境背景**：`10.126.126.1`（wenyan-server 与 Postgres 同机）经 `tun0` **VPN 隧道**可达，
本机为 `10.126.126.3`。这解释了 I/O 类抖动偶发，但**不是本次 30s 超时的原因**。

## 需求

- **R1 超时阈值与实耗匹配**：发布读超时必须显著大于 `/publish` 实耗（43s+），留足余量
  （图更多时更久），杜绝「客户端超时但服务端已写入」。
- **R2 配置必须落到 `.env`**：该超时项当前只存在于 `.env.example`，实际靠代码默认值生效，
  属于隐性配置，需显式化并把默认值改到安全值。
- **R3 超时错误必须可读且防重复**：超时不能吐
  `Error while extracting response for type [java.lang.String]…` 这种框架内部串；
  必须明确告知「服务端可能已写入草稿，请到草稿箱确认后再决定是否重发」。
- **R4 探针不得被发布超时牵连**：探针 `GET /verify` 目前与发布共用同一 `RestClient`，
  R1 调大发布超时会把探针超时一起调到 180s —— 通道不可用时**发布页会被挂住 3 分钟**。
  探针须有独立的短超时。
- **R5 保留非幂等红线**：`/publish` 不自动重试（本条已在 R3 以提示方式覆盖）。
- **R6 前端等待提示与实耗相符**：现有文案「约十几秒…」与 43s 实耗不符，会让用户以为卡死
  而中途刷新/重试，反而制造重复草稿。
- **R7 不扩大范围**：不改渲染链路、不改数据库、不改发布语义与响应键结构。

## 验收标准

- **AC1**（R1）带 7 图文章发布**成功**，`publish_media_id` 落库，状态进入 `PUBLISHED_DRAFT`。
- **AC2**（R1/R3）发布超时阈值 ≥ 实耗 2 倍余量（本次定为 180s），且该值在 `.env` 中显式可见。
- **AC3**（R3）人为把超时改回 30s 复现失败时，错误提示为中文可读语义，
  **包含**「可能已写入草稿 / 请到草稿箱确认」指引，且**不含**框架内部类名串。
- **AC4**（R4）wenyan-server 完全不可达时，`publishOptions` 在 `2 × 探针超时`（默认 ≤10s）内
  返回，不出现 180s 级阻塞。
- **AC5**（R4）探针超时与发布超时为两个独立配置项，互不影响。
- **AC6**（R6）前端发布等待提示与实耗相符（约 1 分钟量级），且不诱导用户中途重复点击。
- **AC7**（R7）回归：预览渲染、配图上传、发布参数接口、正常发布不受影响；
  `mvn -q -DskipTests compile` 与 `npm run build` 均通过。

## 范围外

- 优化 `/publish` 本身的耗时（服务端行为，需改 wenyan-server）。
- 清理已生成的重复草稿（需用户在公众号后台操作；本项目不提供草稿列表/删除能力）。
- 为发布加进度轮询或异步化（另开任务）。
